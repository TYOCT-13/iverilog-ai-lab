# 短周期验证对比：API首轮规划

本计划在新API调用和本轮基线执行前保存。上轮v5的8个开发缺陷上随机与反馈都是8/8，充裕预算检出率已到上限。本轮检验更短周期内的定位能力，结果可以为失败或持平，不要求API胜出。

## 范围与公平性

仍使用四个默认参数模块，按原清单前两个缺陷及正确基线，不能称独立留出。固定、均匀随机、协议随机、API单次规划各做3次重复，seed为0、1、2。每组24缺陷任务、12正确任务，总144任务；分母不随请求拒绝、仿真失败或未检出而改变。所有真实计划同时在正确RTL审核，误报导致该缺陷检出作废。

每组使用同样逐拍参考检查与合约；只改变每任务周期上限：FIFO16、UART48、SPI20、握手8。上限按完整事务的周期需求加边界检查余量确定，详见`spec/agent_smoke_budgets.json`。UART/SPI足够完成完整帧，不能将不可能完成协议的短时间故意当作随机失败。所有策略的API调用/实际周期/墙钟时间仍分别报告，周期上限相同不表示实际资源一样。

参数是在已看过旧开发结果后设计的**新探索性短预算试验**，不是事先未见的盲测，也不能以此替代原充裕预算结果。不得在本轮结果出现后修改周期、种子或缺陷选择，再只发布更好的版本。

API策略沿用v5的system prompt、严格动作schema和独立复位/逐拍执行，每任务只允许一次提案、一次执行；不能据此证明后续失败反馈增益。均匀随机每拍重新随机输入，协议随机保留其现有协议结构，固定策略保留其原模板；都按相同上限归一化。

## 请求预算与冻结

API36任务×1请求，最多36次，不自动重试。既有保守318/360，新增预留36后为354/360，仍有6次余量。使用已有官方DeepSeek Chat接口、deepseek-flash、thinking disabled、非流式、60秒超时、8192输出tokens；没有实付账单则费用null。

新脚本仅组装注册与预算，复用已冻结v5执行和严格汇总，不修改Agent、参考模型、RTL或旧原件。首请求前保存144行、合约、提示指纹、协议设置及输入字节快照；新脚本、此计划和预算配置也进SHA登记。不能因首次失败删去任务。所有重复均报告，不取最好种子，不将24相关任务当作24个独立新缺陷，也不将seed称远程模型确定性。

## 判定与解释

主指标是每策略24个缺陷任务的检出数，同时报告3次各自检出/8、8个缺陷的累计并集、正确任务误报、格式/执行失败、首反例累计周期、实际周期、请求/usage和耗时。没有模型随机数配对，只有3重复，不做普遍显著性或复杂SoC泛化声明。

若API胜均匀随机，只能说在此默认参数开发集、此短预算和此首轮规划方式下观察到优势；必须同时报告固定与协议随机。若持平或落后，原样保存，并以实际失败指导下一轮，不倒改结论。
