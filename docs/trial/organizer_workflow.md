# 真人试用组织流程

目标是查明哪些使用者、在什么环境、为完成什么任务能够使用工具，以及卡在哪里。每条反馈要能追到版本、输入与观察。本次完成率只描述这批样本，不能代替功能正确性验证。

## 一 准备人员和任务

建议一人主持、一人观察；人员少时减少单次任务量。作者可支持，但提示和代操作必须记录。优先邀请未参与对应功能开发的人检验首次使用；团队成员反馈单列为内部试用。

先用 1 人预试任务卡，修正文档后安排 3–5 人正式试用，覆盖新手、RTL 使用者、安装或证据复核需求。人数是项目建议，没有统计代表性保证，也不是比赛规定人数。

每人选择“一个成功流程、一个失败或边界情形、一个角色任务”，详细组合见 `personas_and_coverage.md`。不为凑齐表格让新手做全部高级任务。

## 二 冻结版本和样例

确认 Git 状态并记录 commit。有改动先保存本地提交；必须试未提交版本时，记录 dirty=true 并保留差异，不能只记旧 commit。

```powershell
git status --short
git rev-parse HEAD
# 当前已提交项目代码，写到仓库上一级
git archive --format=zip --output=../icarus-trial-code.zip HEAD
python scripts/build_trial_kit.py
```

`git archive` 不含未提交文件。资料包与程序包分开发送，不直接打包整个工作目录，以免带入私有输入或配置。参与者包不含检查答案；代码仓库仍含作者文档，试用前请参与者不要阅读组织者检查或实验成绩，这不构成严格盲测。

组织者按 `tasks/organizer_checks.md` 预检样例，保存实际返回码和产物路径。预检不计入真人试用人数。错误样例和缺工具场景在独立副本或单次命令中准备，不破坏原 RTL、安装环境或参与者项目。

独立技术审核另需冻结规格、外部来源、文件哈希、变体和原始日志；Git 代码归档不含被忽略的外部实验。审核包按 `docs/review/independent_review_guide.md` 单独准备。

## 三 一次试用的节奏

| 阶段 | 建议时间 | 组织者动作 | 保存内容 |
|---|---:|---|---|
| 说明与同意 | 5 分钟 | 说明目标、退出方式，分别确认匿名引用和录屏 | 基本信息和同意选择 |
| 环境确认 | 5 分钟，安装另计 | 记设备、浏览器、版本、运行模式 | 实际 commit 与工具输出 |
| 独立操作 | 20–35 分钟 | 给任务，不说预期数字，不替人点击 | 原话、时间、结果、协助 |
| 追问 | 5–10 分钟 | 针对卡点问原因 | 原话和证据位置 |
| 核对交回 | 5 分钟 | 核对会话与记录对应，检查隐私 | 原件、导出文件、录屏位置 |

开场可读：“这次主要看工具和说明哪里需要改。做不出来不是你的问题。请说出你正在找什么、哪里不确定。可以请求帮助或随时停止，不需要给正面评价。”

少问“是不是很方便”“是不是省时很多”；改问“刚才期待看到什么”“哪个结果支持判断”“明天遇到同样任务会怎么做”。

## 四 协助和停止

- 先独立探索。参与者求助或长时间无进展时，先问其目标，再按需要提示。
- 提示、解释和代操作分别记在 assistance；次数未知填空，不按 0 算独立完成。
- 安装与网络等待单记；暂停计时要记原因，不为提高速度成绩删除等待。
- 到时间盒或参与者要求停止，保存现场。blocked、partial、skipped 都保留原因和证据。
- DUT 的 FAIL、对比不同或编译失败，与参与者是否完成任务分开。若任务就是找出这类结果及依据，完成后仍可记 completed，工具输出填 objective_result。
- 页面切换和同会话 rerun，与服务重启、浏览器新标签页或新会话不是一回事；只按 T07 实际测试范围评价状态保留。

## 五 保留原件再汇总

同一个人固定一个代号，如 P01；不同会话用 P01-R1、P01-R2。这是命名示例，不是真人记录。补记需标 retrospective 和依据，不能冒充当场计时。

推荐将私人原件放入已被 Git 忽略的位置：

```text
.iverilog-ai/trial-sessions/
  round-1/
    P01-R1.json
    P01-R1/
      feedback-original.docx
      observer-notes.md
      screenshots/
      run-exports/
      raw-recording/
```

原件保存后再转录为 2.0 JSON，让参与者核对。没有给出的信息保留空值，不推断为满意、成功或无问题。`record_kind=human` 是组织者对记录来源的声明，脚本不能验证是否真有人操作，仍要靠原件和记录人员保证真实性。

新汇总脚本默认不抄主观评价；`--public` 仅处理同意匿名引用的会话，分母也只覆盖这些授权样本。录屏同意不等于公开视频或露脸授权；用于比赛成片前另确认用途和范围。

已分配未记录的任务保留为 missing_record；不同任务按实际分配者计数；同人多轮不增加独立人数。共享主机试用不能证明独立安装成功，电脑窄屏也不能算真正手机。

## 六 修复和复测

在 `forms/issue_log.md` 记录现象、任务、版本、证据、严重度、复现步骤、修复提交与复测结果。先处理无法继续和结论误读，再改操作冗余与排版。

修复后用新版本完成相同目标，记录 retest 并关联前次 session_id。首次记录不覆盖。要声称节约时间，应另做同一目标的基线计时，并考虑顺序和熟练度；本套问卷本身不证明节时比例。

汇总到 `results.md` 时列明真实人数、角色、环境、分配任务、首次和复测、协助与失败，以及修复证据。只公开获得许可并去标识的材料。

## 七 后续录像与审核

顺序建议：冻结试用版 → 预试 → 正式试用 → 修复和复测 → 冻结演示版 → 录原片 → 剪辑 → 核对成片。录像与剪辑细节见 `docs/demo/recording_workflow.md`。

独立技术审核可并行：让未参与对应实现或变体编写的人检查冻结的规格、代码和证据。试用回答别人能否完成任务，审核回答证据能否支持结论，视频展示流程，三者分别留记录。
