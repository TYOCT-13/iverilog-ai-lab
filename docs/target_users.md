# 服务对象分析与分场景适配

面向：**决定"这个项目到底给谁用、下一步改什么"的人**（我们自己 + 评委）。

这份文档回答三件事：①这个项目**实际**能服务哪些人（不是"我们希望服务谁"）；
②每类人**今天**用起来会在哪里卡住（逐条对着现有能力核过，不是猜的）；
③针对不同对象分别做什么适配，成本多少、能换回什么。

**证据等级说明**（本文沿用项目自己的三态口径）：标 **【已证】** 的是有代码/产物/实测支撑的；
标 **【假设】** 的是尚未验证的判断，需要在写进报告前用试用或调研坐实。

---

## 1. 先摆事实：我们今天有哪些"接口面"

一个项目能服务谁，取决于它把什么暴露出来了。逐个数：

| 接口面 | 具体是什么 | 谁能用 |
|---|---|---|
| **CLI** | `iverilog-ai` 8 个子命令：`run` / `plan-run` / `compare-rtl` / `report` / `validate-plan`（另有别名） | 工程师、CI、习惯命令行的人 |
| **Python 库** | `import iverilog_ai`，导出 40+ 个公开符号（`VerificationPipeline`、`IcarusExecutor`、`generate_testbench`…） | 写脚本/做二次开发的人 |
| **网页** | `streamlit run ui/app.py`，五个页签（概览 / 设置 / 质量 / 验证 / 手册），支持上传自定义 RTL | 不想碰命令行的人、演示场合 |
| **本地 HTTP 服务** | `python -m iverilog_ai.ai.debug_server`，回环地址上的**离线** AI 规划接口 | 想把本项目接进别的工具的人 |
| **产物** | `result.json` / `report.md` / `report.html` / VCD / 证据包 / 基准矩阵 | 复核者、留档 |
| **离线可跑** | 默认不发网络请求；没有密钥也能跑完整 AI 路径 | 学生、内网、教学机房 |

**关键约束（决定了哪些人我们服务不了）**：唯一的 PASS/FAIL 权威是本地 `iverilog`/`vvp`；
不做时序签核、不做布局布线、不做形式化等价证明、不做代码覆盖率。**专业验证团队用 VCS+VCS/UVM
的那套流程，我们进不去，也不该假装能进。**

## 2. 服务对象清点：六类真实对象

### 对象 A：用 AI 生成 RTL 的开发者 ⭐ 最贴合赛道

- **他们的工作**：把需求丢给大模型 → 拿到 Verilog → 能编译 → **但不知道对不对**。
- **"要完成的任务"（JTBD）**：*"给我一个不依赖我信任 AI 的、能跑出来的对错判断。"*
- **为什么是我们**：这是本项目**架构上专门解决**的问题——参考模型复算覆盖 AI 期望值（
  门 3）、三态证据等级、三层结论口径，全部是为"AI 的数字不能作数"设计的。**【已证】**
- **今天卡在哪**（对现有能力核过）：
  1. 上传 RTL 后**必须手填 DUT 合约**（端口/方向/位宽/时钟/复位）。虽然已有
     `extract_contract_draft` 自动提草稿，但入口在网页深处，CLI 没有对应命令。**这是最大摩擦点。**
  2. **没有"AI 版 vs 我原来的手写版"的一键路径**。`compare-rtl` 需要用户自己准备
     `--plan` 和 `--contract` 四个参数——对"我只想让 AI 重写这个模块"的人来说门槛过高。
  3. 报告里"AI 期望值准确率"是有的，但没有面向这个场景的**说明页**告诉用户
     "哪一层结论能信、哪一层不能"。

### 对象 B：开源 RTL 项目的维护者 / 贡献者 ⭐ 最贴合"开源"

- **他们的工作**：收到一个重写模块的 PR，或者自己想重构，**上游项目根本没有 testbench**。
- **JTBD**：*"我怎么知道行为没变？我不想为了这个 PR 先写一套 TB。"*
- **为什么是我们**：`compare-rtl` **不需要上游有 testbench**——它从合约生成 TB，把同一份
  TestPlan 喂给两份 RTL，判"行为等价"还是"只是写法不同"。这是市面上少见的组合。**【已证，
  15/15 案例上跑通】**
- **今天卡在哪**：
  1. 没有 **GitHub Action**。我们自己是 CI，但没给别人可复用的入口——而"开放成果"正是赛道
     评分点，一个 Action 比一段说明文字硬得多。
  2. 没有**目录级批量**对比。`available_modules` + `extract_contract_draft` 都在，但没串成
     "扫一个仓库 → 每个顶层模块提合约 → 跑对比 → 出报告"。
  3. 没有可直接贴进 PR 的**结论模板**（一段 markdown，说明测了什么、结论是什么、边界在哪）。

### 对象 C：数字电路 / Verilog 学习者

- **他们的工作**：课程作业要交 RTL + testbench，**TB 写不对，仿真报错看不懂**。
- **JTBD**：*"别让我先学会写 TB 和读波形，先让我的模块跑起来并告诉我错在哪。"*
- **为什么是我们**：完全离线、不需要密钥、有中文手册与 15 个可对照的参考案例。**【已证】**
- **今天卡在哪**：
  1. 网页**默认把全部能力摊开**（静态审查、覆盖率、综合、行为对比…），对第一次用的人是过载。
  2. 失败信息虽然有结构（检查项/第几拍/期望/实际），但**没有"这对应 RTL 里该看哪里"的白话指引**。
  3. 15 个内置案例没有"照着改"的入口（学习者最想做的就是改一个数、看结论怎么变）。
- **注意**：这一类的**用户量最大但差异化最弱**——学习工具非常多，而且与本赛道"AI+开源"的
  关联最远。**【假设：需要在报告里论证它为什么值得占篇幅】**

### 对象 D：课程教师 / 助教

- **他们的工作**：批 50 份作业，判定要一致，学生不服要能解释，还要防雷同。
- **JTBD**：*"给我一份可复现、逐条有据、能贴在班群里解释的判定结果。"*
- **为什么是我们**：确定性判定 + 逐条证据 + **行为等价对比天然是反雷同工具**（结构性相似 ≠
  行为一致，反之亦然）+ 完全离线（不用把学生代码传到云端）。**【已证：能力都在；假设：教学
  场景的需求强度未调研】**
- **今天卡在哪**：**没有批量模式**。一个文件一个文件跑，50 份作业不可行。也没有班级级报告。

### 对象 E：CI / 自动化流水线（非人类，但是真实服务对象）

- **JTBD**：*"这次提交能不能过？给我机器可读的结论。"*
- **现状**：CLI 退出码 0/1 已有、`--print-json` 已有。**【已证】**
- **今天卡在哪**：没有官方 Action；静态审查结果没有 **SARIF** 输出（无法进 GitHub Code
  Scanning 的 PR 注解）。

### 对象 F：评审 / 第三方复核者

- **JTBD**：*"我不想信你的话，我想自己跑一遍。"*
- **现状**：证据包、5 个可复现矩阵脚本、Normify 结构图、700 条测试（700 passed / 1 skipped）。**【已证】**
- **今天卡在哪**：没有一页"**10 分钟复核指南**"（先跑哪条命令、期望看到什么数字、对不上怎么办）。

## 3. 收敛：六类对象其实是三套能力

把上面的"为什么是我们"横向看，会发现六类对象只对应**三套底层能力**：

| 底层能力 | 服务谁 | 独特性 |
|---|---|---|
| **① 权威预言机 + 三态证据 + 三层口径** | A、D、F | 高——"AI 的数字不作数、结论分层、证据等级如实"是别人没做的 |
| **② 从合约生成 TB + 行为等价对比** | B、D（反雷同）、A（AI 版 vs 手写版） | 高——**不需要被测项目自带 testbench** |
| **③ 44 条静态规则 + AI 复核建议层 + 离线可跑** | C、E、全体 | 中——静态规则很多工具都有；我们多了"建议层"与离线 |

**这个结构决定了投入产出比**：对象 A 与对象 B **共用能力 ①②**，所以"适配 A" 和 "适配 B"
不是两个功能，而是**同一套工作流面对两种入口**。边际成本极低，而覆盖的场景价值翻倍。

**结论性建议**：主打 **A + B**，把 C/D/E/F 作为"同一套能力的不同包装"顺带覆盖，
**不为 C 单独造一套学习工具**。

## 4. 分场景适配清单（按性价比排序）

### 4.1 P0：把"验收一份 RTL"从库函数提升为一等工作流（服务 A + B）

**现状**：`compare-rtl --plan --contract --user-rtl --reference-rtl` 四个参数，
用户得先自己造计划与合约。

**适配**：新增 CLI `iverilog-ai verify-diff`，把 4 步合成 1 步：

```
iverilog-ai verify-diff --baseline rtl/old.v --candidate rtl/new.v \
    [--spec spec/old_spec.md] [--plan plan.json] [--contract contract.json] \
    --out-dir runs/verify-diff
```

- 缺合约 → 自动从 `--baseline` 提草稿，**打印出来让用户确认**（不静默采用）
- 缺计划 → 用离线确定性规划器生成，**并标注证据等级**
- 跑完输出：`identical` / `different` + **差异表（第几拍、哪个检查项、期望、两侧实际）**
  + 一份可贴进 PR 的 markdown
- 退出码：等价 0 / 不等价 1 / 不可判定 2

**成本**：小（底层 `compare_rtl_behavior`、`extract_contract_draft`、
`offline_provider` 都已存在，主要是编排 + 输出格式化）。**收益**：同时打通 A、B 两个场景。

### 4.2 P0：网页新增"两种入口"的场景化首页（服务 A + B）

**现状**：五个页签按**功能**组织（概览/设置/质量/验证/手册），用户得自己拼流程。

**适配**：在概览页顶部加一个**场景选择**（三个大按钮，选完只显示相关控件）：

| 场景 | 面向 | 选中后做什么 |
|---|---|---|
| **「AI 帮我改了 RTL，验一下」** | A | 两个文件框（原来的 / AI 改的）→ 一键 `verify-diff` → 结论 + 差异表 |
| **「我只有一份 RTL，先跑起来」** | C、A | 上传 → 自动提合约草稿（可编辑）→ 生成计划 → 跑 → 三层结论 |
| **「批量看一个仓库」** | B、D | 选目录 → 列出顶层模块 → 批量提合约 → 批量对比 → 汇总表 |

**成本**：中（网页改动 + 新编排函数复用 4.1）。**收益**：把"功能清单"变成"任务入口"，
对评委也是**需求论证最直观的证据**。

### 4.3 P1：GitHub Action（服务 B + E）

`action.yml` + 一段 workflow 示例：在 PR 上跑 `verify-diff`，把结论写成 PR 评论草稿与
job summary；可选把静态审查输出成 **SARIF**。

**成本**：中（要设计 Action 的输入输出、跑通一次真实 PR）。**收益**：赛道"开放成果 /
社区贡献"这一项**最硬的交付物**——别人能用，不只是"我们开源了"。

### 4.4 P1：10 分钟复核指南（服务 F）

`docs/reproduce_in_10_minutes.md`：5 条命令、每条期望看到什么数字、对不上怎么排查。

**成本**：很小。**收益**：直接回应"验证方法"与"开放价值"两个评分点。

### 4.5 P2：教师批量模式（服务 D）

CLI `iverilog-ai grade --dir submissions/ --golden rtl/ref.v --report class.md`：
批量跑 + 班级汇总表 + **两两行为相似度矩阵**（`rtl_compare` 结构相似 + `behavior_compare`
行为一致，两者交叉看）。

**成本**：中。**收益**：报告很好写、有画面感。**但需求未经调研**——建议先做 4.1–4.4，
用它换来的试用反馈再决定要不要做。

### 4.6 明确不做（写进报告当"边界"，而不是漏掉）

- 不替代 UVM/VCS 等专业验证流程；不做时序签核、形式化等价、代码覆盖率；
- 不做"AI 自动修 bug 并保证修对"——我们只提供**候选修复 + 相同的 TestPlan 复验**
  （`repair_compare` 已有，且明确标"仍需人工审查"）；
- 不替用户决定"这份设计能上板"。

## 5. 对报告的影响（顺带解决一个已知短板）

`docs/competition/competition_readiness_assessment.md` 自己写过一句：
**"目标用户描述目前散落在文档里，没有成型的需求论证"**（"问题与场景价值"这一项自评 8–11 分，
满分 15）。

本文档就是补齐它的材料。写进报告时按这个顺序：

1. **用户与场景**：一句话点明主打 **A（AI 生成 RTL 的验收）+ B（开源 RTL 的行为等价回归）**，
   说明为什么选这两类（它们共用同一套底层能力，且直接对应赛道关键词"AI"与"开源"）；
2. **需求优先级表**（照抄参考报告的"指标 / 目标 / 说明"格式）：

   | 需求 | 目标 | 说明 |
   |---|---|---|
   | 判断一秒钟内可信 | 结论分层 + 证据等级三态 | 不把"AI 说的"当证据 |
   | 不要求用户先写 testbench | 从合约生成 TB | 上游项目往往没有 TB |
   | 判定必须可复现 | 同一输入同一结论，退出码稳定 | CI 与学生作业都要求 |
   | 成本可承担 | 全程本地、离线可跑 | 学生/内网/教学机房 |
   | 结论要能被追问 | 逐条落到"第几拍、期望、实际" | 评审与教师解释 |

3. **验证方法**：另两类对象（D 教师、F 复核者）作为**次要对象**，用同一套能力验证；
4. **未达标项前置**：D 的需求论证尚未调研——如实写，比硬凑一个漂亮结论可信。

## 6. 一页速查

- **能服务六类人，但只有三套底层能力**；其中"权威预言机"与"免 TB 行为等价对比"是别人没有的。
- **最该做的两件事**：把 `compare-rtl` 升级成 `verify-diff` 工作流（A+B 共用），
  再把网页从"功能页签"改成"场景入口"。
- **最该交付的开源物**：GitHub Action —— 它是"社区贡献"这一评分点的硬证据。
- **明确不做的**：专业验证流程、时序/形式化/覆盖率、自动修 bug。
- **诚实标注**：对象 D（教师批量）的需求尚未调研，别在报告里写成已验证。
