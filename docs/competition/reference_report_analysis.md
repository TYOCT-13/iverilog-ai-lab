1. **唯一一份真正的 AIC 报告是 15 页整**——正好卡在官方"正文建议 15 页以内"。说明国二

   不是模型更强，是想清楚了该放弃什么。**

**注意它没有封面页、没有目录。** 第 1 页顶部直接是标题行 `AC4.2-算法应用创新-应用创新方案`，
下一行就是"一、项目概述 / 1.1 背景与意义"。**省下的 2 页全给了正文。**

> 就是纯亏损。** 我们的报告不设独立封面页（团队名/编号/作品名按大纲要求放首页抬头即可）。

### 2.2 排版与版式（这几条是"看起来专业"的一半）

- **页眉每页都写赛道编号**：左 `AiC 2025 AICOMP` 标识，右 `全球校园人工智能算法精英大赛
  算法创新赛 / AC4.2-算法应用创新-应用创新方案`。评委翻任何一页都知道这是哪条赛道。
  → 我们应写 `算法主题赛 / AIC·AI+开源`。
- **三级编号严格**：`一、`（章，大号加粗）→ `3.1`（节，加粗）→ `3.1.1`（小节）。
  正文段落用 `（1）（2）（3）` 分点。
- **图表密度极高**：15 页 48 张图。第 5 页正文只有 **62 个汉字** + 3 张图/表。
  **规律：文字只写"论证"，结构交给图，数据交给表。**
- **功能模块统一两行式**：每个模块都是
  `（1）技术细节：……` / `（2）功能亮点：……`。5 个模块格式完全一致，读者扫一眼就懂。
- **表格全部无表题、直接插在正文流里**，表头加粗居中，正文用宋体小四。
- **图片成组铺满**：Grad-CAM 示例是 3×3 九宫格一页铺满（第 11 页）。

### 2.4 另外几处结构技巧

- **架构图（第 5 页）**：四层横向堆叠的方框图（应用层 → 服务层 → 算法层 → 数据层），
  层内 3 个方框，层间箭头标注协议（gRPC / HTTP-RESTful / 加载模型文件）。**先给图，再给
  "各层职责"文字**。
- **数据流不用时序图，用 9 步编号表**（第 5 页 3.2.1）：

  | 步骤 | 名称 |
  |---:|---|
  | 1 | 用户通过应用层的 Web 接口上传眼底图像 |
  | 2 | 请求抵达服务层的 API 网关，网关将请求转发给业务逻辑引擎 |
  | 3 | 业务逻辑引擎创建一个异步任务，并将其放入任务队列，立即返回"处理中"状态，避免请求阻塞 |
  | 4 | 任务队列的 Worker 从队列中取出任务，首先调用算法层的图像预处理服务进行质量检测与标准化 |
  | 5 | 预处理通过后，Worker 调用 AI 模型推理服务，该服务从数据层的模型文件库加载轻量化的 ONNX 模型，执行推理 |
  | 6 | Worker 随后调用可解释性服务，为推理结果生成 Grad-CAM 热力图 |
  | 7 | Worker 将所有结果（分级、风险、热力图）返回给业务逻辑引擎 |
  | 8 | 业务逻辑引擎根据预设规则库生成健康建议，将完整结果结构化后存入缓存服务，并写入关系数据库，同时将报告文件存入对象存储 |
  | 9 | 用户可通过查询接口从缓存或数据库中获取最终报告 |

  **比画时序图省一半时间，且信息量更大**——这是整份报告里最实用的一个技巧。
- **测试方案用三维度矩阵表**（第 9 页 5.1）：`功能测试 / 性能测试 / 可靠性测试` 三档，
  每档先写跨列的"测试目标"行，再写具体测试项 + 检验方法。
  - 功能性：图像质量筛查 / DR 分级功能筛查
  - 性能：端到端流程筛查 / 系统并发处理能力筛查
  - 可靠性：持续运行稳定性测试 / 数据一致性测试
- **团队分工表匿名合规**（第 9 页 4.2）：`成员A（微电子科学与工程）/ 成员B（软件工程）/
  成员C（通信工程）` + 职责。**不写学校、不写真名**——正好满足规则"技术报告、演示视频、
  答辩 PPT 中不得出现学校名称、LOGO 与指导教师信息"。
- **参考文献 8 条混排**：中文期刊（协和医学杂志、浙江医学）+ 国际顶会顶刊
  （JAMA ×2、ICML、ECCV、ICCV）。**不是凑数，每条都能对上正文的技术选择。**
- **附录只写一句**："本项目的数据集资料、核心代码等材料已在网盘链接中给出……为节省篇幅
  此处不再展示。" → **15 页的约束下，附录用链接换篇幅。**

### 2.5 它的弱点（我们必须在这些地方超过它）

拿国二不等于完美。逐页看下来有四处硬伤：

1. **性能数字没有实验协议**。"平均推理延迟 18ms""10 台设备时 23ms"——没说硬件型号、
   测试集规模、重复次数、方差。**这是不可复现的数字。** 我们任何数字都必须带
   "命令 + 机器 + 次数 + 方差"。
2. **没有消融实验（ablation）**。它说"注意力机制提升鲁棒性""蒸馏实现轻量化"，但**没有任何
   一张"去掉 X 之后指标掉多少"的对照表**。省二门槛就写着"有消融实验"，这份国二其实没做足。
   我们的 benchmark 天然能做：**同一批 83 个缺陷，开/关参考模型预言机、开/关结构化断言，
   检出数各是多少**——这是最硬的消融。
3. **没有失败案例**。全篇只讲成功。而真实工程的价值恰恰在"踩坑—定位—修复—回归"。
   我们手上有 3 个可写的真实事故（离线分支喂了罐头计划导致 `rst_n` 未知端口、文本框
   widget key 冲突、断言模板字段与校验器不一致导致"点两次才成"），每一个都有
   症状 → 根因 → 修复 → 回归测试的完整链条。
4. **开源合规基本没写**。全文只在"意义"里提了一句"自主知识产权"，附录里没有许可证、
   没有第三方资源清单。**而"规范使用开源资源"正是我们赛道的主评分点。** 这是我们的主场，
   必须写足。

### 2.6 一个必须规避的技术事故：PDF 元数据泄露实名

`AIC-国赛-技术方案.pdf` 的文档属性里写着：

```
author: 曹慕凡
creator: WPS 文字
producer: macOS 版本26.2（版号25C56） Quartz PDFContext
creationDate: D:20251226112107+08'00'
```

正文里已经匿名成"成员A/B/C"，**但导出 PDF 时把作者真名写进了元数据**。规则第（九）条
要求评审材料不得出现学校名称、LOGO 与指导教师信息——真名虽未明文禁止，但配合
"producer: macOS 版本26.2"这类信息，匿名性是被削弱的。

**我们的动作**：提交前用脚本检查并清空 PDF 元数据（Title/Author/Subject/Keywords/
Creator/Producer），并把这一步写进提交检查清单。已落地为
`scripts/check_submission.py`（见第 6 节 A5）。

**顺手对我们的现有草稿做了同样的体检**（`docs/competition/technical_report_draft.md`
渲染出的 14 页 PDF）：

```
已检查 draft.pdf（14 页，802 KB）
[提示] pages/room-left: 只有 14 页，距 15 页上限还空 1 页
[提示] metadata/dump: {"title": "", "author": "", "subject": "", "keywords": "",
                       "creator": "", "producer": ""}
[警告] anonymity/keyword: 第 1 页 命中「学校」：…文中不含学校名称、校徽与指导教师信息…
[警告] anonymity/keyword: 第 6 页 命中「指导教师」：…按规则做匿名处理：不出现学校名称…
结果：0 error / 4 warning
```

两个结论：**① 我们的元数据是干净的，页数也已经在限内**（比参考报告还少 1 页）；
**② 4 条警告全部来自我们"声明自己匿名"的那句话本身**——正文里写"文中不含学校名称、
校徽与指导教师信息"，反而把这三个词写进了正文。这是自指的假阳性，但也不划算：
既占篇幅，又让任何做关键词扫描的人（或评委）看到这些词。**建议把这句声明移到提交说明/
README 里，报告正文不写。**

## 4. 其他赛事的报告格式（只取"摘要页"这一件事）

`Competition-Summary` 里的三份报告允许几十页，但**摘要页的写法可以直接借鉴**：
"总体引入一段 + 对于问题一/二/三各一段（每段写清用了什么方法、得到什么结论）+ 关键词"。
篇幅整整一页，独立成页。

泰迪杯那份（22 页）是**任务驱动型**：封面 → 目录 → 摘要 → `1 任务一 / 2 任务二 / …` →
参考文献，每节直接对应赛题的一个小问。当赛题是"给定 N 个任务"时用这个骨架。

**对我们的意义**：我们的官方大纲九章已经固定，不需要换骨架；但**在第一章之前插入一个
不超过 200 字的"作品速览"框**（问题 / 做法 / 结果各一句）是低成本的加分项——评委在
15 页里找重点的时间很短。

## 5. 反面对照：`Noise-FGVC` 公开的两个"提分漏洞"

该仓库的 `漏洞与做法` 是本届最有价值的一份**反面材料**，作者明确说"我们并没有在赛事中
使用这类不合规的行为"，但把方法写出来了：

1. **预训练权重来源造假**：赛题只允许 ImageNet-1k 预训练权重，他们失误用了 ImageNet-21k，
   发现 5000 类上"出奇的高、拟合极快"，于是讨论了"重命名成 1k 的样式再封装 API 上传"。
   ——**同源权重的版本差异也能带来 1–2 个点**。
2. **数据溯源反推答案**：官方数据集是对原数据集**改名 + 删减**，图片尺寸字符串对每个类别
   唯一，因此可通过信息编码回溯原始数据集拿到真实标签。"这也是为什么能够出现满分的提交。"

**这两条对我们的价值不是"可以抄"，而是"必须防"**：

- 我们的赛道叫 **AI+开源**，"规范使用开源资源"是明写的评分点。**评委一定会看我们有没有
  如实披露资源来源、版本、许可证**。上面两条恰好是"来源不实"的典型。
- 我们的《开源及第三方资源使用清单》应当**主动点出这两类风险并声明我们的做法**：
  ①模型/权重只通过官方渠道获取并记录版本与 hash；②数据集来源、许可证、是否允许再分发
  逐条列明；③不使用"仅公开可访问"但无明确授权的内容（这一条官方大纲第七节原话）。
- 这一节写在报告里，等于**把一个通用合规声明变成了针对真实已知漏洞的具体回应**，
  比"我们遵守开源协议"这种空话有说服力得多。

## 7. 一页速查：从这四份材料里能直接搬走的东西

1. **15 页就写 15 页**，不设封面目录，标题行 + 正文直接开始。
2. **页眉写赛道全称**，让评委任何时候都知道在评哪条赛道。
3. **文字论证、图管结构、表管数据**；一页 60 个汉字 + 3 张图是正常密度。
4. **"指标 / 目标 / 说明"表**把模糊目标变硬，"维度 / 数据 / 成果"表收尾。
5. **数据流写成 N 步编号表**，比时序图省时间且更清楚。
6. **功能模块统一两行式**（技术细节 + 亮点/可验证性）。
7. **测试方案用三维度矩阵**（功能 / 性能 / 可靠性）。
8. **团队分工匿名**（成员A/B/C + 专业 + 动词化职责）。
9. **参考文献真引**，中英文混排，每条对得上正文的技术选择。
10. **附录用链接换篇幅**。
11. **导出 PDF 前清空元数据**——它漏了作者真名；我们已有 `scripts/check_submission.py` 把关。
12. **补上它没有的两块**：消融实验表、失败案例复盘。
