# 往年获奖报告是怎么写的：公开证据 + 可迁移模式 + 我们的差距清单

> 调研日期：2026-09-20。调研对象：第八届全球校园人工智能算法精英大赛**算法主题赛 · AIC·AI+开源**
> 赛道，以及报告正文已经公开、可以逐页对照的相邻赛事（全国大学生智能汽车竞赛、开源类项目结项）。
>
> 本文只写**能核验**的东西：能拿到原文的写原文出处，拿不到的直说拿不到，不编"某届特等奖报告"。

---

## 一、先说清楚：这个赛道往届的获奖报告，公开能拿到什么

| 想找的东西 | 是否公开 | 实际情况 |
|---|---|---|
| 官方**技术报告参考大纲** | ✅ 公开 | 附件2《AIC·AI+开源技术报告参考大纲》（2026-08-12 版，5 页）。**本文第二、三节全部基于它的原文** |
| 官方**评分项与分值** | ⚠️ 部分公开 | 规则附件给出分值结构；我们已在 `submission_outline.md` 里逐项映射（15/20/20/25/15/5） |
| 往届**获奖名单** | ✅ 公开 | 组委会在官网公示获奖名单 PDF（如第七届总决赛名单）。能看到**作品名称、队伍、学校、奖项** |
| 往届**获奖作品的技术报告原文** | ❌ 不公开 | AIC 只公示名单与新闻稿，**没有作品报告展示页、没有代码仓库链接**。因此"照抄某届获奖报告的结构"这条路走不通 |
| 往届**获奖作品的新闻稿** | ✅ 公开 | 高校新闻稿会写清获奖项目的**领域与做法**（例：第七届国家一等奖"基于AI的智能旅行规划"、二等奖"多源异构数据协同的视频目标跟踪"，见[兰州交通大学 2025-12-10 新闻](https://news.lzjtu.edu.cn/info/1077/20098.htm)） |
| 相邻赛事**报告正文** | ✅ 公开 | 全国大学生智能汽车竞赛把参赛队伍技术报告与评分表公开在同一份云盘目录里（含 `技术报告` 与 `评分细目`），是唯一能"逐页看获奖报告怎么排版怎么写"的稳定来源 |

**结论（很重要）**：这个赛道没有"往届报告范文"可抄。真正决定获奖的是官方大纲里那些**反复出现的要求**，
加上"评委能不能在你的报告里快速找到可核验的证据"。所以下面第二节从官方原文里提炼隐性评分点，
第三节给出相邻赛事获奖报告的可迁移写法，第四节是**我们报告逐节对照后的差距清单**。

## 二、官方大纲里被反复强调的 8 个隐性评分点（原文摘录）

我数了附件2里各要求的出现位置与措辞，下面 8 条是"没写就丢分、写了没证据也丢分"的：

1. **不是简单调用接口**（三.4 明文）："说明 AI 技术与开源资源如何形成完整方案，**而不是简单调用接口、
   直接部署项目或进行界面包装**"。→ 我们的"AI 提出、开源工具裁决"分工正是对这一条的直接回答，必须在
   报告里用**一张边界图 + 三句不可替代性**讲透。
2. **自主开发与权利边界**（三.3）：要求"清晰区分第三方部分、通用 AI 工具完成部分、团队自主设计/开发/
   调试/数据加工/验证部分"。→ 需要一张**三栏边界表**，不能只写一句"全是我们做的"。
3. **如何验证 AI 输出**（三.1 明文设问）："说明为什么需要 AI，**以及如何验证 AI 输出**"。→ 这是本赛道
   的核心设问。我们的三重门（严格 Schema → 合约匹配 → 参考模型复算覆盖）就是答案，要写成"门"而不是"功能"。
4. **哪些目标尚未达到**（五.3 明文）："说明作品解决了什么问题、达到什么效果，**以及哪些目标尚未达到**"。
   → 主动写未达标项是加分动作，不是自曝其短；官方把它写进大纲说明评委在等这一段。
5. **不以篇幅评分**（大纲说明段）："不以报告篇幅、图片数量或材料数量作为评分依据"。→ 堆材料无收益，
   15 页内把数据写扎实即可。
6. **上游贡献要给链接与状态**（六.3）："如向上游项目提交 Issue、Pull Request…**请提供链接和状态**；
   如暂无上游贡献，可说明作品供他人复用的方式和价值"。→ 我们目前没有上游 PR，就必须把"复用方式"写实。
7. **许可证义务逐条核查 + "公开可访问 ≠ 有授权"**（七.1、七.2 两处明文）：两节都写了这句话。→ 资源清单
   的"关键义务/限制"与"合规状态"两列必须逐条填，不能只写"已遵守"。
8. **AI 辅助开发要说明审核过程**（四.3）："使用生成式 AI 或智能体辅助开发的，应说明使用环节及团队的
   审核、修改、验证、来源与权利核查工作，并说明对所使用模型、平台或 API 适用许可和服务条款的遵守情况"。
   → 三件事都要落地：环节、审核动作、服务条款遵守。

另外两条硬性形式要求（违反进不了复赛）：**封面字段齐全**（团队名称/编号/作品名称/参赛方向/日期）、
**《开源及第三方资源使用清单》用官方 8 列表头**（序号、资源名称及类型、版本/来源、许可证/授权类型、
使用/开放方式、关键义务/限制、团队自主修改或开发内容、合规状态）。

## 三、相邻赛事获奖报告的可迁移写法（10 条）

来自报告正文公开可查的赛事（智能汽车竞赛技术报告与评分表、开源类项目结项报告）。这些不是 AIC 的规定，
而是"评委翻页时能快速建立信任"的通用写法，逐条都能落到我们的稿子上：

| # | 写法 | 为什么有效 | 我们该怎么做 |
|---|---|---|---|
| 1 | **第一页给"结果速览"框**：3–5 个headline 数字 + 一句定位 | 评委一天看几十份，先给结论再讲过程 | 在 §1.3 前加一个 5 行速览框（83/83 手写测试台、0 误报、700 passed / 1 skipped、15/15 对齐、在线探索性 97.0% vs 固定 83.6%） |
| 2 | **方案论证用对比表**：候选方案 → 判据 → 选型结论 | 证明你**选过**，而不是只会一种 | §2.1 把"三种现有做法"改成三列对比表（可信度/覆盖度/离线可核验/成本） |
| 3 | **一张主线框图 + 标注边界** | 评委靠图建立整体认知，边界展示工程深度 | §2.2 的架构图必须标出"AI 可影响 / AI 不可影响"，并把 Icarus 画成判决权威 |
| 4 | **测试方法独立成节**：条件、仪器/工具版本、用例、判据 | 数据可复现 = 数据可信 | §5.2 补一张"测试条件表"（工具版本、机器、每个案例的向量预算、重复次数、判据阈值） |
| 5 | **原始数据 + 派生结论分开** | 允许评委抽查原始记录 | §5.3 每个数字后给出**产物文件名**（matrix.json / result.json / 实验 md），附录给路径 |
| 6 | **"问题→定位→修法"过程记录**，至少 3 个真实案例 | 区分"真做过"与"包装" | §4.3 列 3 个真实事故：离线计划驱动 `rst_n`、`signal_implies` 字段自相矛盾、全仓扫描导致 17 秒重跑 |
| 7 | **主动写未达标与适用边界** | 降低评委的"夸大"扣分风险 | §5.3（5）已有，建议提到 §5 开头，并给出"若要达标需要做什么" |
| 8 | **可复现优先**：一键命令 + 期望输出 | 评审能自己跑，是最强证据 | §9.2 命令已具备；建议每条命令后面写"期望输出"，让评委能对照 |
| 9 | **上游贡献/复用**要给链接或明确说没有 | 编造会被查 | §6.3 改为"暂无上游 PR（如实说明）+ 三条可复用路径（基准集/规则包/测试计划 JSON 格式）" |
| 10 | **版本迭代时间线**（表格：日期→版本→做了什么→证据） | 证明周期内持续投入 | §4.3 用 git 历史生成一张 6–8 行时间线表 |

## 四、我们报告逐节对照后的差距清单（可直接当施工单）

对照物：官方大纲九节（附件2 原文）+ 上面 10 条写法 + 我们自己的 `submission_outline.md`。

| 节 | 现状 | 差距 | 动作 |
|---|---|---|---|
| 封面 | 有团队名称/编号/作品名称/方向/日期占位 | 无异常 | 定稿前填报名系统里的名称与编号 |
| （新增）速览 | **无** | 缺"第一页结论" | 加 5 行速览框（写法 #1） |
| （新增）摘要 | **无** | 官方另需 ≤300 字作品简介 | 报告首段加 200–300 字摘要；简介单独交 |
| 一、作品概述 | 三类用户痛点 + 目标 + 三条亮点，写得扎实 | 亮点里数字可再前置 | 亮点三条各补一个可核验数字 |
| 二、需求分析与总体方案 | 需求分析有；方案图有；成本有 | 缺**对比选型表**；架构图缺"AI 边界"标注 | 改表（#2）+ 图上标边界（#3） |
| 三、AI 与开源资源 | AI 作用、资源清单、权利边界、融合方式四节齐 | 权利边界建议做成**三栏表**；"如何验证 AI 输出"要更醒目 | 三栏表 + 把"三重门"提为该节小标题 |
| 四、设计与实现 | 5 条关键实现 + 分工记录 | 缺**时间线表**与**提示词设计**小节；过程记录里真实事故可再具体 | 加时间线（#10）+ 提示词设计（官方四.2 明文要求） |
| 五、成果展示与验证 | 数据最全（固定矩阵、对齐、在线实验、负例） | 缺测试条件表；未达标项位置偏后 | 加测试条件表（#4）；未达标项前置（#7） |
| 六、创新性与开放价值 | 三点创新 + 开放成果 + 复用 + 维护计划 | 上游贡献写法要更明确（暂无→复用路径） | 按 #9 改写 |
| 七、合规、安全与风险 | 四小节齐，含"公开可访问≠有授权" | 风险节缺"不宜使用场景"的清单式呈现 | 列表化（技术限制/适用边界/不宜场景三列） |
| 八、总结与展望 | 有总结 + 后续计划 | 无异常 | — |
| 九、附录 | 资源清单、仓库与运行说明、测试记录、插图、参考文献 | 缺"受限提交说明"的显式"不适用"声明 | 加一行"不涉及受限内容" |
| 全篇 | 15 页内、匿名已自查 | 目录缺失（>10 页建议有） | 加一页目录（不计入正文工作量） |

**施工优先级**（按"评委翻页顺序 × 丢分风险"排）：

1. 速览框 + 摘要（第一印象，30 分钟能写完）
2. 架构图边界标注 + 对比选型表（对应官方三.4、二.2 两个明文要求）
3. 测试条件表 + 期望输出（把我们最强的 25 分证据变成"可抽查的"）
4. 三人权边界表 + 时间线表 + 过程事故（对应官方三.3、四.3）
5. 未达标项前置 + 复用路径改写（对应五.3、六.3）
6. 目录与版式收尾

## 五、常见扣分点（相邻赛事公开评审意见的共性）

| 扣分点 | 具体表现 | 我们的现状 |
|---|---|---|
| 只有功能、没有可核验数据 | "实现了 X" 但没有数字/产物路径 | ✅ 我们数据最全，保持 |
| 把"调用开源工具"写成融合 | 官方三.4 点名：简单调用接口/直接部署/界面包装 | ✅ 我们有"分工"叙事，需在图上再强调 |
| 权利边界含糊 | 第三方/AI 生成/自主混在一起 | ⚠️ 需改成三栏表 |
| 许可证只写"已遵守" | 没有版本、来源、义务逐条 | ✅ 资源清单已按 8 列编制 |
| 夸大：未做时序/上板却说"验证通过" | 评委现场追问即崩 | ✅ 我们明确写"未运行" |
| 篇幅超标或版式混乱 | 形式审查风险 | ⚠️ 定稿后核对页数与 PDF 体积 |
| 匿名信息泄露 | 报告/视频/PPT 出现学校、导师、学号 | ✅ 全库已检索，需在定稿前再扫一次 |
| 没有真实用户/场景支撑 | 读起来像技术说明书 | ✅ 三类用户痛点 + 开发过程实录 |
