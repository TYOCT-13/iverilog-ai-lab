# Icarus 智测后续改进方案

> 规模化成果路线和阶段验收请同时参阅 [`scale_up_roadmap.md`](scale_up_roadmap.md)。

更新日期：2026-09-05

> 进度更新（2026-09-06）：P1 参考模型、测试执行覆盖率、失败原因解释、受控断言模板、失败周期波形摘要、多文件 RTL 导入、顶层 module 选择和 DUT contract 表格编辑已实现并通过自动化测试。

## 1. 项目定位

Icarus 智测是围绕 Icarus Verilog 开源生态构建的非官方 AI 辅助 RTL 验证扩展。系统采用“AI 负责提出测试、严格数据合约负责约束、Icarus Verilog/vvp 负责裁决、结构化结果负责复现”的技术路线。

当前项目已经完成以下基础闭环：

```text
RTL/规格与 DUT contract
        ↓
AI 生成 TestPlan
        ↓
严格 Schema 校验与确定性规范化
        ↓
自动生成受控 testbench
        ↓
iverilog 编译与 vvp 仿真
        ↓
结构化 PASS/FAIL、报告和 VCD 波形
```

本方案的目标是将项目从“可运行的技术原型”提升为“可复现、可评测、可展示、可协作的比赛提交级开源项目”。

## 2. 当前能力基线

- 支持模十计数器、交通灯、简单 ALU、101 序列检测器四类参考设计。
- 建立 50 个可编译 RTL 缺陷版本。
- 支持固定、随机和离线 Mock AI 三种测试策略实验。
- 支持 OpenAI-compatible Responses API 和 Chat Completions API。
- 支持 DeepSeek 接口路径、模型列表查询、JSON 输出和脱敏诊断。
- 支持自定义 `.v/.sv` RTL 导入、端口解析草稿和 DUT contract 人工确认。
- 支持 AI TestPlan、自动 testbench、真实 Icarus/vvp 仿真。
- 支持 Markdown/HTML 报告、结构化失败反例和 VCD 波形下载。
- 支持失败后由 AI 补充测试向量，再由用户确认后重新执行。
- 具备安全路径、非 shell 执行、超时、输出截断、API Key 不落盘等安全边界。

## 3. 总体优先级

| 优先级 | 方向 | 目标 |
|---|---|---|
| P0 | 比赛交付与复现 | 陌生评委能在短时间内理解、安装和复现 |
| P0 | 实验可信度 | 用真实在线模型和更大缺陷集证明 AI 的实际价值 |
| P1 | 验证正确性 | 解决 AI 同时生成输入与期望输出带来的测试预言机风险 |
| P1 | 覆盖率与波形 | 将“通过多少检查”升级为更完整的验证证据 |
| P1 | 自定义 RTL 通用性 | 提升端口/参数/多文件工程的导入能力 |
| P2 | AI 诊断与修复 | 构建失败分析、候选修复、重新验证、人工确认闭环 |
| P2 | 开源社区建设 | 形成可贡献、可审查、可发布的真实开源工作流 |
| P3 | FPGA 工具链扩展 | 增加综合、时序分析和可选上板验证，严格区分证据等级 |

## 4. P0：比赛交付与复现

### 4.1 重构 README

README 建议采用以下结构：

1. 项目一句话简介。
2. 要解决的问题与使用场景。
3. 30 秒核心流程图。
4. 当前功能和明确边界。
5. Windows/PyCharm 图形化快速开始。
6. 命令行快速开始。
7. 固定案例演示。
8. 自定义 RTL 演示。
9. 实验结果表。
10. 安全设计。
11. 项目目录结构。
12. 许可证、贡献方式和未来计划。

验收标准：

- 新用户只看 README 可在 10 分钟内启动 Streamlit。
- README 包含真实页面截图、流水线图、VCD 波形截图和一份报告示例。
- 明确声明“Icarus 仿真通过不等同于综合、时序收敛或 FPGA 上板通过”。
- 明确区分离线 MockProvider 与真实在线模型实验。

### 4.2 一键启动

- 增加 Windows 启动脚本，自动检查 Python、虚拟环境、依赖和 Icarus 路径。
- 增加环境自检页面，显示 Python、iverilog、vvp、写入目录和网络 Provider 状态。
- 保留手动安装方法，避免启动脚本成为唯一入口。

验收标准：

- 双击脚本或在 PyCharm 中运行一个入口即可打开网页。
- 缺少依赖时给出中文提示，不产生伪成功结果。
- 不修改用户现有 Codex/OpenAI 配置，不保存 API Key。

### 4.3 比赛材料

- 完成技术方案 PDF。
- 完成答辩 PPT。
- 录制 3～5 分钟演示视频。
- 准备一页项目海报或系统总览图。
- 保存一次成功案例和一次缺陷检出案例的完整证据包。

演示顺序建议：

```text
固定案例通过
→ 自定义 RTL 导入
→ AI 生成 TestPlan
→ 自动生成 testbench
→ Icarus 仿真
→ 展示结构化失败/通过记录
→ 展示 VCD 波形和报告
→ 展示失败后 AI 补充测试
```

## 5. P0：实验可信度

### 5.1 扩展缺陷基准

- 将缺陷数量扩展到至少 30，当前已达到 50；后续继续增加协议和时序类缺陷。
- 增加计数器、FSM、握手协议、FIFO、脉冲检测、边沿检测、去抖、UART/SPI 等类型。
- 每个缺陷必须记录缺陷类型、预期行为、触发条件、修改位置和检测结果。
- 参考设计与缺陷设计必须使用相同的评测预算。

### 5.2 真实在线模型实验

- 至少评测 2～3 个可稳定调用的真实模型。
- 每个模型至少执行 10 个固定 seed 或等价重复实验。
- 不把 MockProvider 结果宣传为真实 AI 模型能力。
- 保存模型名、接口协议、生成时间、合法率、token 使用量和费用估算；不得保存 API Key。

建议指标：

| 指标 | 含义 |
|---|---|
| TestPlan 合法率 | 模型输出通过严格 Schema 的比例 |
| 参考误报率 | 正确 RTL 被判失败的比例 |
| 缺陷检出率 | 缺陷 RTL 被测试发现的比例 |
| 首次发现时间 | 从计划生成到首个失败反例的耗时 |
| 测试向量效率 | 单位向量或单位 token 检出的缺陷数 |
| API 延迟 | 请求开始到合法 TestPlan 生成完成的耗时 |
| 成本 | 每次计划和每个检出缺陷的估算费用 |
| 稳定性 | 多次运行结果的均值、标准差和失败率 |

### 5.3 公平比较

- 固定策略、随机策略、AI 策略使用相同最大向量数、周期数和运行时预算。
- 区分计划生成时间和仿真执行时间。
- 报告每个模型的原始逐次结果，而不只报告最好成绩。
- 公开未检出的缺陷，不隐去失败实验。

## 6. P1：参考模型与测试预言机

当前 AI 可能同时生成输入和期望输出，存在期望值错误风险。需要增加独立参考模型：

- 为计数器、ALU、序列检测器和交通灯建立 Python reference model。
- TestPlan 的输入向量送入 reference model 生成或校验 expected。
- 对 AI expected 与 reference model expected 不一致的情况标记为 `plan_inconsistent`，不直接进入 PASS 判定。
- 自定义 RTL 在没有参考模型时明确标记“期望值来自规格/人工/AI”的证据等级。

验收标准：

- 内置案例的 expected 可由参考模型独立复算。
- AI 给出错误 expected 时，在运行前被发现或在报告中明确标注。
- 报告能区分“模型生成测试”和“参考模型提供预言机”。

## 7. P1：覆盖率、断言与波形

### 7.1 覆盖率

- 增加向量覆盖率、输出检查覆盖率和状态/转移覆盖率统计。
- 对无法从 Icarus 直接获得的代码覆盖率，明确说明采用的近似方法。
- 将覆盖率写入 `pipeline_result.json` 和 Markdown/HTML 报告。
- 在网页中显示覆盖率摘要，而不只显示 `30/30`。

### 7.2 断言

- 第一阶段支持受控、模板化的即时断言。
- 不允许 AI 直接向 testbench 注入任意 SVA/Verilog 代码。
- 断言必须来自预定义模板或经过解析验证的结构化描述。

### 7.3 VCD 波形

当前已支持 VCD 生成与下载，后续继续增加：

- 网页内信号列表和时间范围选择。
- 失败周期附近的波形摘要。
- 报告中附带 VCD 路径、SHA-256 和文件大小。
- 可选集成 GTKWave 启动说明，但不依赖 GTKWave 才能运行核心流程。

当前已提供离线的失败周期附近结构化摘要（基于 records，不替代 VCD 证据）。

## 8. P1：自定义 RTL 通用性

### 8.1 端口解析

- 完善 ANSI/non-ANSI 端口声明解析。
- 支持共享方向声明、参数化位宽和常见 SystemVerilog 类型。
- 支持多个 module 时由用户选择顶层。
- 无法确定的字段必须标记为待确认，不进行危险猜测。

### 8.2 多文件工程

- 支持上传多个 RTL 文件和 include 文件。
- 建立项目内受控源文件清单。
- 自动分析 module 依赖，但最终顶层和 include 目录由用户确认。
- 继续使用 `SafePathPolicy`，禁止路径逃逸和 shell 参数注入。

### 8.3 DUT contract 编辑体验

- 将原始 JSON 编辑框升级为端口表格表单。
- 可配置方向、位宽、signed、时钟、边沿、复位方式和复位电平。
- 表单与 JSON 双向同步。
- 提供 contract 下载、上传和版本标记。

## 9. P2：AI 失败诊断与修复闭环

当前已支持“失败后补充测试向量”，后续增加：

```text
仿真失败
→ 提取脱敏失败反例
→ AI 生成诊断假设
→ 生成补充测试
→ 用户确认
→ 再次仿真
→ 比较两次证据
```

修复能力必须遵守：

- 原始 RTL 永不自动覆盖。
- AI 只能生成候选补丁或结构化修复建议。
- 候选补丁在项目内临时副本执行。
- 修复前后都运行相同回归集。
- 只有所有参考回归通过且目标失败消失时，才标记为“候选修复验证通过”。
- 最终应用到原 RTL 必须由用户人工确认。

验收标准：

- 不允许无限 AI 循环，调用次数和费用有明确上限。
- 报告保存失败指纹、补充计划和前后结果对比。
- AI 解释不能替代 Icarus 工具证据。

- `CHANGELOG.md`

- 创建正式版本标签和 release notes。
- 不伪造多人 Commit、Issue 或 PR；协作记录必须来自真实开发过程。

## 11. P3：综合、时序与 FPGA 上板

这是后续扩展方向，不应与当前 RTL 仿真结论混淆：

- 可选接入 Yosys 进行综合可行性检查。
- 可选接入 Vivado 或其他 FPGA 工具链进行综合、实现和时序分析。
- 报告分别显示 simulation、synthesis、timing、bitstream、hardware 状态。
- 没有真实运行的阶段必须显示 `not_run` 或 `inconclusive`，禁止推断为通过。

## 12. 文档一致性整改

当前 README、架构文档和阶段报告需要同步新增能力：

- 自定义 RTL 上传与 contract 草稿。
- VCD 波形生成与下载。
- DeepSeek/Chat Completions Provider 兼容。
- 模型列表和脱敏请求诊断。
- 失败后 AI 补充测试。
- 最新自动化测试数量和真实运行日期。

同时需要修正过期描述，例如把“只运行仓库白名单案例”更新为“自定义 RTL 被复制到项目受控目录、经 contract 确认后执行”；安全边界和限制也应同步更新。

## 14. 完成定义

项目达到比赛提交级别时，应满足：

- 陌生用户能按照 README 成功启动并完成一次固定案例验证。
- 自定义 RTL 可以安全导入、确认 contract、生成测试并完成仿真。
- 正确参考设计无误报，缺陷基准有公开、可重复的检出结果。
- 至少两个真实模型完成公平、可审计实验。
- 所有 PASS/FAIL 来自真实工具输出，而非 AI 自评。
- 文档、测试结果和网页功能保持一致。
- 许可证、第三方依赖和开源贡献规则清晰。
- 技术方案、PPT、演示视频和证据包齐全。

## 15. 不应做的事项

- 不把 API Key 写入代码、`.env`、日志、报告或提交记录。
- 不伪造模型成绩、工具输出、多人协作记录或比赛结果。
- 不把 RTL 仿真通过宣传为综合、时序或上板通过。
- 不让 AI 输出直接成为 shell 命令或未经验证的 Verilog/SVA。
- 不自动覆盖用户原始 RTL。
- 不隐瞒未检出缺陷、无效计划和失败实验。
