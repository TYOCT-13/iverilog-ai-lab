## 一、作品概述

### 1.0 作品服务谁（先说清楚，后面所有取舍都从这里来）

一个工具能服务谁，取决于它把什么能力暴露出来了。本项目按"要完成的任务"识别出**四类对象**，
**两类主打**：

| 对象 | 要完成的任务 | 为什么我们合适 |
|---|---|---|
| **① 用 AI 生成 RTL 的开发者**（主打） | "大模型给的 Verilog 能编译，但它到底对不对？"今天的做法是让同一个模型再写一遍 testbench——**让被考核的对象兼任考官** | 第三门就是为"AI 的数字不能作数"设计的：参考模型复算覆盖 AI 期望值、三态证据等级、四层结论口径 |
| **② 开源 RTL 维护者 / 贡献者**（主打） | "这个 PR 重写了模块，行为变了吗？可上游根本没有 testbench" | `verify-diff` **不需要被测项目自带 testbench**：从 `module` 头自动提合约、生成计划，两份 RTL 跑同一份计划后逐项 + 逐拍比对 |
| ③ 数字电路 / Verilog 学习者 | "测试台写不对，报错也看不懂" | 完全离线、无需密钥、有中文手册与 15 个可对照案例；失败被翻成"下一步看哪一行" |
| ④ 课程教师 / 助教 | "50 份作业要批，判定要一致，学生不服要能解释" | 确定性判定 + 逐条证据 + 批量批改与相似度线索 + 全程离线（不把学生代码传云端） |

**为什么主打 ①②**：它们**共用同一套底层能力**（权威预言机 + 免 testbench 的行为等价对比），
所以为一个对象做的适配几乎原样服务另一个；而它们又正好分别对应本赛道的两个关键词——"AI"
与"开源"。对象 ③④ 用同一套能力的不同包装覆盖。

**诚实标注（未达标项前置）**：

- 对象 ③④ 的用户需求来自真实试用反馈与课程场景推断，**尚未做正式调研**，本报告不对其
  需求强度下结论；
- 对象 ④ 的**批量批改**已实现（`iverilog-ai grade`：批量行为对比 + 两两相似度线索表），
  但**没有在真实班级里试用过**，因此不声称它在 50 人规模下的实际体验；
- **正文超过建议的 15 页**（当前页数见本地验证记录）；
- **上游 Issue / Pull Request 尚未提交**（见 §6.3）；
- 其余未达标项集中列在 §7.4。

### 1.1 背景与问题

围绕 Icarus Verilog 做验证的人，几乎都会卡在同一处：写得出 RTL，写不动测试台。

我们在自己的数字电路学习与项目实践中反复遇到三个具体问题：

**（1）测试台的门槛高于设计本身。** 一个 30 行的模十计数器，要覆盖复位、使能保持、
回绕三类行为，手写测试台通常需要 80 行以上，而且每换一个设计就要重写一遍。初学者
的常见结果是"RTL 写完了，但只做了肉眼检查"。

**（2）"AI 说验证过了"无法核验。** 通用大模型可以直接生成 testbench，但它同时会生成
**期望值**——而期望值一旦是错的，错的期望值会把错误的设计判成"通过"，或者把正确的
设计判成"失败"。这不是假设：本项目在真实在线模型实验中就观测到过这类现象（详见
§5.3）。**让被考核的对象同时担任考官，是这套做法最根本的缺陷。**

这一条在 2026 年变得比以往更迫切：AI 已经能写出一份**能编译、看起来合理**的 RTL，
唯一的缺口是"没人验"。而**验收一份 AI 改写的 RTL，恰恰是最需要"比两份实现"而不是
"从头写一个测试台"的场景**——这正是对象 ①② 共用的那套能力。

**（3）现有工具链缺一段自动化。** Icarus Verilog 是成熟、可靠、完全开源且可脚本化的
仿真器，它的定位是"给定 testbench，给出结果"。从"我想验证什么"到"可执行的
testbench"这一段，目前没有开源工具覆盖。上游开源 RTL 项目普遍**没有测试台**，
也就没有任何低成本的行为回归手段。

### 1.2 目标、参赛方向与作品形态

**参赛方向**：（二）AI 开发工具与开源协作。

**作品形态**：命令行工具 + 网页应用 + GitHub Action + 可复用基准集与规则包。

**核心功能**：把自然语言的验证目标，转换为**受严格约束**的结构化测试计划，再由确定性
代码生成 testbench，交给 Icarus Verilog 真实编译与仿真，最后产出可追溯的证据与报告。
针对对象 ②，另有一条**不需要输入测试台**的路径：从 RTL 自动提合约、生成计划，
把同一份计划喂给两份 RTL，判定行为是否一致。

一句话概括本项目的分工主张：**AI 提出测试假设，开源仿真器作出判决。**

### 1.3 核心亮点

1. **AI 不参与判分。** PASS/FAIL 只由 Icarus 的编译/仿真结果与结构化断言决定；AI 的期望值
   被独立的确定性参考模型复算覆盖，不一致只记诊断，不影响结论。
2. **15 案例 / 83 可复现缺陷，实跑 83/83 检出、0 误报、0 不可判定**（§5.3）。
3. **证据分层，并把"没做的"写出来。** 五层证据表把"时序分析 / 布局布线 / 上板验证"显式标
   "未运行"，避免把"仿真通过"或"综合通过"误读为"能上板"（§5.5）。
4. **离线可完整复现。** 自带离线调试模型服务（只监听回环、不需要密钥、不联网），评委可在
   无凭据环境下跑通全部流程与实验。
5. **验收一份 RTL 不需要先写测试台。** `iverilog-ai verify-diff` 一条命令判断两份 RTL 行为
   是否一致（合约与计划都可自动准备），产出可直接贴进 PR 的对比报告。
6. **结论口径分四层、措辞互不重叠。** 运行状态 / 比对情况 / 设计结果 / 对比结论各用一套
   不共用的词，避免同一个 `passed` 被读成三件事（§4.2）。

## 二、需求分析与总体方案

### 2.1 需求分析

**（1）现有做法与痛点**

| 现有做法 | 主要痛点 | 需求优先级 |
|---|---|---|
| 手写 testbench | 工作量大、边界易漏、换设计即重写 | 覆盖度 |
| 通用大模型直接写 testbench | 期望值不可信；无法离线复核；结论不可追溯 | **可信度** |
| 商业仿真器的 AI 助手 | 闭源、需授权、无法审计判决路径 | 可信度 |
| 上游项目"没有测试台"就放弃回归 | 重构与 AI 改写无法验收 | **可信度** |

我们的优先级排序是 **可信度 > 覆盖度 > 效率**：一个"看起来自动化了但结论不可信"的
工具，在验证场景里比没有工具更危险。

**（2）需求量化（每一行都对应一处可核验的实现）**

| 需求 | 目标 | 说明 |
|---|---|---|
| 结论必须可信 | AI 期望值一律由独立参考模型复算覆盖 | 第三门；`SUPPORTED == AUTHORITATIVE` 有断言守着 |
| 结论必须可读 | 四层措辞互不重叠，不出现"同名不同义" | `core/labels.py` 为唯一措辞来源 |
| 不要求用户先写测试台 | 从 RTL 自动提合约、按合约生成测试计划 | `verify-diff` 默认路径 |
| 判定必须可复现 | 重放同一输入与测试计划 → 同一结论；退出码稳定 | 当前回归结果见 `docs/experiment/local_validation_2026-10-04.md`；5 个矩阵脚本 |
| 判定必须可追问 | 每条失败落到"第几拍 / 期望 / 实际 / 失败指纹" | 结构化记录 + 失败解释 |
| 成本学生可承担 | 全流程本地、离线可跑；在线开销透明 | 无密钥跑通完整 AI 路径；费用按核验价目表给区间 |

### 2.2 总体方案

![图 1 系统架构](figures/fig1_architecture.png)

系统分四层，关键设计是**把 AI 关在第一层里**。各层职责如下：

| 层 | 职责 | AI 能影响吗 |
|---|---|---|
| **① AI 规划层** | 只输出结构化 JSON 测试计划；离线时用按合约生成激励的确定性规则引擎，需要真实模型能力时接任意 OpenAI 兼容接口 | **能**（唯一一层） |
| **② 合约与安全边界** | 字段/位宽/取值域严格校验 + 与 DUT 合约端口逐一对齐；**不生成、不拼接 Verilog**；路径白名单；执行不经 shell | 不能 |
| **③ 确定性执行层** | Icarus 编译 + vvp 仿真作为唯一判决权威；参考模型独立复算期望值并覆盖 AI 数字 | 不能 |
| **④ 证据与报告层** | 结构化记录、波形语义分析、静态质量审查、分层证据表、四层结论口径 | 不能 |

**一次验证的数据流**（10 步，每一步的产物都可单独审计）：

| 步骤 | 发生什么 |
|---:|---|
| 1 | 用户给出验证目标（一句话）与 DUT 合约（端口/时钟/复位） |
| 2 | AI 规划层据此产出 **TestPlan JSON**：每条向量写明驱动哪些端口、跑几拍、期望什么 |
| 3 | **门 1**：严格 Schema 校验（字段名、类型、位宽、取值域）——杜撰字段或越界取值直接拒绝 |
| 4 | **门 2**：与 DUT 合约逐端口对齐——端口名或方向对不上直接拒绝 |
| 5 | **门 3**：参考模型按同一份激励独立复算期望值，**覆盖** AI 给出的数字 |
| 6 | **门 4**：结构化断言只允许五种受限模板，模型无法注入 Verilog/SVA 代码 |
| 7 | 确定性模板生成 Verilog-2001 testbench；每条断言输出一行 `IVERILOG_AI_RESULT {json}` |
| 8 | Icarus 编译 → vvp 仿真（固定参数列表、不经 shell、带超时与输出上限） |
| 9 | 严格解析器消费结构化记录；结构化断言在采样序列上判定；波形语义分析读 VCD |
| 10 | 产出报告（四层结论口径 + 证据等级）、失败反例（带失败指纹）、VCD 与证据包 |

## 三、AI 技术与开源及第三方资源选择

### 3.1 AI 技术的作用

AI 在本项目中承担三件事，每一件都配了对应的**验证手段**——这是本项目与"让模型直接写
testbench"最根本的分工差别：

**（1）把自然语言验证目标转成结构化测试计划。**

- **技术实现**：模型的唯一输出是一份 JSON（`vectors[].inputs` 驱动哪些端口、跑几拍，
  `expected` 期望什么），受严格 Schema 约束；提示词里内置全部 44 条规则的上下文与实测
  编码约定。
- **为什么需要 AI / 怎么验证**：边界条件的枚举空间大且依赖设计语义，人工穷举成本高——
  这正是生成式模型擅长的"按语义提出候选假设"。验证方式是**四重门控**（下表），
  以及离线消融对执行链的检验：**离线规则计划 + 权威预言机可检出 76/83，无期望值组为 0/83**。
  后者没有可比较检查项；该对照不使用真实 LLM，不能证明模型增益。真实模型结果见 §5.3(3)。

**（2）提出边界激励。**

- **技术实现**：模型在计划里显式写出每条向量的 `rationale`（人读的意图说明），
  例如"FIFO 写满""计数器回绕""101 序列重叠检测"。
- **怎么验证**：与仓库自带的人工边界激励做同口径对照。**实测：通用激励比人工边界激励
  少检出 7 条，且少检出的全是"要精确时序或边界序列才能触发"的缺陷**（§5.3）——
  这里比较的是离线规则激励与人工激励，不能直接推断真实 LLM 的能力。

**（3）解释失败原因。**

- **技术实现**：把结构化失败记录（检查项 / 第几拍 / 期望 / 实际）翻成"下一步看哪里"，
  指出该信号在 RTL 里被赋值的行号，并给出复现命令。
- **怎么验证**：措辞上严格守住一条线——只写"**是「被赋值的位置」，不一定是「出错的
  位置」**"（问题也可能在激励、复位或上游信号），并有测试钉住这句。

**四重门控——AI 输出的验证链**（这是本项目的核心工程内容）：

| 门 | 机制 | 拦截什么 |
|---|---|---|
| 第一门 | 严格 JSON Schema 校验（字段名、类型、位宽、取值域） | 格式错误、杜撰字段、越界取值 |
| 第二门 | DUT 合约匹配（端口名与方向必须真实存在） | 模型杜撰端口别名（如把 `enable` 写成 `en`） |
| 第三门 | 确定性参考模型复算并**覆盖** AI 期望值 | **AI 写错期望值导致假通过或假失败** |
| 第四门 | 结构化断言只允许五种模板化检查 | 模型注入自由 Verilog/SVA 代码 |

第三门是决定性的。内置案例的参考模型都已与参考 RTL **逐拍对齐**（15/15，多个随机
种子零差异），因此在这些内置案例中用模型复算值作为权威期望值。离线消融中，
有参考模型期望值时检出 76/83；移除期望值后没有可比较检查项，检出为 **0/83**。

### 3.2 开源及第三方资源选择

### 3.4 融合方式：为什么不是"简单调用接口"

1. **AI 输出必须穿过确定性边界才能执行。** 模型输出必须通过 Schema 与合约双重校验，
   再由确定性代码生成 testbench；模型从不接触 Verilog 语法层，因此**结构上不可能**
   注入代码、命令或路径。
2. **开源仿真器是判决权威，AI 只是假设提出者。** 即使模型完全不可靠，工具仍然可用
   （退化为"人工设计激励 + 真实仿真裁决"）。
3. **参考模型独立复算，堵住"写错期望值"这条路。** 这是同类工具普遍缺失的一环，
   也是我们在真实模型实验中观测到问题之后专门补上的一环——其作用见 §5.3 的消融实验。

### 4.1 核心功能与流程

| 功能 | 输入 → 输出 |

| 结构化断言 | 受限模板（信号相等/稳定/永不置高） → 通过/失败记录 |
| 波形语义分析 | VCD → 边沿统计、毛刺判定、相位偏差、双波形差异、失败时间窗 |

| 分层证据 | RTL 源码 + Yosys → 综合状态、单元统计、五层证据表 |
| 行为级对比 | 两份 RTL + 同一 TestPlan → 逐检查项差异 + 波形差异 |

### 4.2 关键实现

每个关键实现都按「**技术实现 + 为什么这么做**」两段写——后者才是评审真正想看的判断。

**（1）确定性 testbench 生成器。**

- **技术实现**：生成器不解析、不拼接模型提供的任何文本，只把已通过校验的**标量数据**
  填入固定模板；每条断言输出一行 `IVERILOG_AI_RESULT {json}`，由执行器的严格解析器消费。
- **为什么这么做**：这样"AI 生成的内容"与"可执行代码"在**结构上**被彻底分离。不是靠
  提示词叮嘱模型"不要写危险代码"，而是让模型**根本没有写代码的通道**。

**（2）权威预言机门控。**

- **技术实现**：只有**与 RTL 逐拍对齐**的参考模型才能覆盖期望值；未对齐的设计返回空
  字典，调用方回退为 AI 期望值并如实标注 `expectation_source="ai_generated"`。
- **为什么这么做**：模型一旦与 RTL 差一拍，就会把"参考设计通过"改写成"参考设计失败"，
  **比没有预言机更糟**。放宽这个集合的方法只有一个——让模型逐拍对齐（"对齐一个、加入
  一个"）。离线消融中，有参考模型期望值时检出 76/83；无期望值时没有可比较检查项，检出为 0/83。

**（3）IEEE 1364 非阻塞赋值语义对齐。**

- **技术实现**：把同一组向量同时喂给参考模型与 RTL，**逐拍**比较可观测输出，要求零差异。
- **为什么这么做**：对齐过程中共发现并修掉 8 个模型错误，其中三个同一根因——
  **同一时刻对同一变量的非阻塞赋值，其右侧读到的是旧值**。例如 UART 发送器写
  `bit_idx <= bit_idx + 1` 之后同拍读 `frame[bit_idx+1]`，用的是**旧**的 `bit_idx`；
  模型若用新值取位，输出就整体错开一拍。SPI 的 `sclk`/`mosi`、去抖的 `key_state` 都栽在
  同一处。**这类问题只有逐拍对照才能发现，肉眼看波形很容易误判成"差不多对"。**

**（4）路径与进程安全。**

- **技术实现**：所有外部进程以固定工具名 + 参数列表启动，**不经过 shell**；输入与工件
  路径走白名单策略；每个进程带超时与输出上限；不自动覆盖原始 RTL。
- **为什么这么做**：工具要跑用户上传的 RTL，"不执行来路不明的代码"不能只写在文档里——
  必须让**执行路径上根本没有拼接字符串的机会**。

**（5）噪声校准作为交付物的一部分。**

- **技术实现**：静态规则与波形毛刺判据各经历三轮校准，逐条核实命中是否为真。
- **为什么这么做**：初版规则对仓库内 84 个 RTL 文件报出 317 条命中，含大量误报
  （如把注释结尾 `*/` 当成除法、把合法写法误判为锁存器）。**"规则命中数"本身不是成果，
  "命中里有多少是真的"才是**——所以校准过程也写进交付物（§5.4）。

**（6）三个真实事故的复盘。** 三条都来自真实使用（含本人自测与外部试用反馈），每条都能
在仓库提交历史里找到对应修复与回归测试。**写进报告是因为"踩了什么坑、怎么定位、怎么
防止复发"比一串功能清单更能说明工程能力**，也说明判据确实在被真实场景压测，而不是只在
测试集上好看。完整复盘表（症状 / 根因 / 修复 / 回归）见**附录 §9.6**。

三条各自暴露一类问题：① **离线路径喂了写死的演示计划**（选择分支时没跟着合约走）；
② **Streamlit 的 widget 与 `session_state` 生命周期冲突**（先建控件再写同名键必然报错）；
③ **提示词与校验器各写了一份字段表**——这一条最值得记：我们一度把它归因为"模型写错
字段"，复核后发现**提示词自己就把该字段列进了模板**，模型只是照着写，**缺陷在本项目
一侧**。报告按修复后的事实陈述，不把自己的缺陷记成模型能力问题。

### 5.2 验证方法

| 方法 | 做法 | 能回答的问题 |
|---|---|---|
| **固定矩阵基准** | 15 个参考设计 + 83 个缺陷变体，逐个跑同一固定激励 | 能不能检出已知缺陷，会不会误报 |

| **外部复核** | 10 分钟复核指南（`docs/reproduce_in_10_minutes.md`）：5 条命令 + 期望数字 + 对不上怎么反馈 | 别人能不能自己验一遍 |

**（2）离线消融：激励与参考模型的作用**（`python scripts/run_ablation_matrix.py`）

上面那张表说明手写 testbench 在内置基准上的检出结果。本节用同一批 83 个缺陷做三组实测，
另计算 A 与 C 的并集；**不是四档实测，也没有调用真实 LLM**。B/C 的计划相同，仅改变期望值来源；
A/C 比较手写测试台与离线规则计划两种路径，不能视为只改变一个变量的严格消融。

| 配置 | 激励来源 | 期望值来源 | 缺陷检出 | 参考误报 | 不可判定 |
|---|---|---|---:|---:|---:|
| A `handwritten-tb` | 人工设计的边界激励（仓库自带 testbench） | 人工写死在 testbench 里 | **83 / 83** | 0 / 15 | 0 |
| B `ai-plan-plain` | 离线规划器按合约生成 | **没有期望值** | **0 / 83** | 0 / 15 | 0 |
| C `ai-plan-oracle` | 离线规划器按合约生成 | 参考模型独立复算并覆盖 | **76 / 83** | 0 / 15 | 0 |
| A ∪ C（推导值，非实测组） | 合并 A、C 检出集合 | — | **83 / 83** | — | — |

**结果与边界：**

1. **B → C：0 → 76。** 两行的**激励完全相同**（同一份计划、同一个随机种子），
   只把期望值从"没有"换成"参考模型独立复算"。B 组没有可比较检查项，不能检出缺陷；
   C 组得到 76/83。这说明当前离线执行链需要独立期望值，**不等于测得 LLM 的能力提升**。
2. **A → C：83 → 76。离线规则路径少检出 7 条。** 两条路径都使用确定的期望值，
   但测试台、激励与观测方式不同。少检出的 7 条都需要精确时序或边界序列：
   异步复位在两沿之间断言（`mod10_counter`）、同步器级数与释放窗口（`sync_reset` ×2）、
   抖动序列长度（`debounce`）、展宽期内重触发（`pulse_stretcher`）、写满 off-by-one
   （`sync_fifo`）、紧急抢占时刻（`traffic_light_emergency`）。逐条明细见**附录 §9.8**。
   这组对照只支持"当前离线规则路径未覆盖全部人工测试边界"，不外推为真实模型的结论。
3. **A ∪ C = 83/83，规划器独立贡献 0 条。** 这个结论对我们不利，但必须如实写：
   **当前离线确定性规划器的价值不在"发现人没想到的缺陷"，而在"不用人手写 testbench 就能
   拿到 76/83"**。真实模型的实验另列于 §5.3(3)，不能用本节离线消融替代其能力证据。

**参考模型对齐**：15/15 个内置案例的参考模型与 RTL 在 4 个确定性随机种子上逐拍
零差异，因此全部可以作为权威预言机；建模覆盖与权威集合完全一致（有测试断言防止放宽）。

**（3）预算对齐后的重跑与同轮数子集**（每计划刺激预算一致、固定分母、参考告警作废）：

旧的比较不成立——三组各自决定跑多久（实测同案例 fixed/random/ai/online 分别是 4/12/12/18 个向量），
分母还由"实际产出的行"决定，请求失败会让分母一起缩小。改造后：每个案例的总刺激周期
**先按规格定好**（见表下方说明），各策略共用同一个值；计划执行前归一化（超长尾部截断、
不足按末态保持补齐）；分母来自 `benchmarks/manifest.json` 登记的 (案例, 变体)；
计划生成失败/编译失败/超时/零可比较检查项一律记"不可判定"并按未检出计入；
参考设计自己出现功能不一致时，该 (案例, 轮次) 的变体检出作废。

因此“每计划同预算”不能写成“多轮并集的总预算相同”。以下完整保留原始结果：

|---|---:|---:|---:|---|---:|---:|
| 固定向量（人工），1 轮 | 67 | 57（85.1%） | 85.1% | 85.1%–85.1% | 0 | 0 |
| 随机向量，5 轮 | 67 | 57（85.1%） | 78.2% | 74.6%–83.6% | 0 | 0 |

**（5）负例验证**（证明判据不是"永远通过"）：

- 不可综合的 RTL（变量上界的 `while` 循环）→ 综合层报 **失败**；
- 语义等价但写法不同的重写（多出一个内部辅助信号）→ 行为对比判 **一致**；
- 已知缺陷（极性反转、计数差一）→ 行为对比判 **不同**，并定位到具体信号与拍；
- **候选编译不过** → 行为对比判 **未取得可比证据**（退出码 2），而不是"行为不同"——
  这两件事必须分开：前者是"没跑起来"，后者是"跑起来了但结果不同"。

**（6）尚达到不了的目标**：不做时序签核、不做代码覆盖率、不做 CDC 形式化、参考模型只
覆盖内置案例——完整边界清单见 §7.4。

### 5.6 外部模块验证（别人写的 RTL，不是我们自己的）

内置基准是我们自己写的，容易被质疑"是不是照着自家测试台长的"。因此补了一组**外部模块**：
`alexforencich/verilog-uart`（MIT，Verilog-2001，单时钟），接收侧 `uart_rx` 与发送侧 `uart_tx`。

流程与内置案例完全一致：**人工合约**（显式写明复位为**高有效 + 同步**、`prescale` 为 16 位）
→ 激励 → Icarus → 行为对比。此外每个模块配一份**手写规格测试台**（只依据 UART 规范，
不看 DUT 内部实现）：`uart_rx` 用"一帧好帧 + 一帧停止位为 0"共 11 项检查；
`uart_tx` 用**环回**（tx 发、rx 收，收到的字节必须等于发出的）共 10 项检查。

| 模块 | 功能变体 | `verify-diff` 判"不同" | 规格测试台抓到 | 等价改写 | 编不过的输入 |
|---|---|---:|---:|---|---|
| `uart_rx`（握手 + 状态机） | 5 | **5/5** | 5/5 | 判"一致" | 判"未取得可比证据" |
| `uart_tx`（握手 + 状态机） | 5 | **5/5** | 3/5 | 判"一致" | 判"未取得可比证据" |
| `priority_encoder`（**参数化输入**，纯组合） | 5 | **5/5** | 5/5 | 判"一致" | 判"未取得可比证据" |

合计 **15 个功能变体，`verify-diff` 判"不同" 15/15**；三个基线全部通过规格测试台；
三个等价改写全部判"一致"（无误报）；三个编不过的输入全部判"未取得可比证据"
（**没有被误判成"行为不同"**）。第三个模块是纯组合逻辑、没有时钟也没有复位，
行为由 `WIDTH` 与 `LSB_HIGH_PRIORITY` 两个参数决定——规格测试台里同时实例化两个参数取值，
直接检验"参数化"本身；合约里不写 clock/reset，**不写等于"没有"，而不是猜一个出来**。

**两个判据的盲区不同，正好互补**——这是这次外部验证最有价值的一条观察：

- 环回测试台**漏掉"位周期少一拍"**：接收侧是 8 倍过采样，能容忍 ±1 拍的波特率误差，
  环回照样通；而 `verify-diff` 把 `txd` 波形与基线**逐拍**比对，立刻看出不同。
- 环回测试台**漏掉"busy 信号不清"**：我们的检查只覆盖了"发送中 busy 为 1"，
  没覆盖"发完归 0"；`verify-diff` 把 `busy` 当输出端口比对，直接抓到。
- 反方向：这一批里 `verify-diff` 没有漏的，**10/10 全部判"不同"**。

**如实写三条限制**：（1）两个模块**来自同一个上游仓库**，只覆盖"握手 + 有限状态控制"，
参数化输入一类尚未覆盖；（2）变体由开发者本人构造，**未经独立复核人审核**，
因此只能称为"人工变异"，不能称为"真实社区漏洞"；（3）每个模块只跑了一个激励计划，
本结果**不能**外推为"能检出这些模块的所有缺陷"。

外部验证还暴露了两个**测试设计**层面的坑，我们都记了下来：测试字节用了位序回文 `0xA5`
（正反读一样），于是"数据位序写反"的变体在行为上与基线**完全相同**；以及测试台
`@(posedge clk); tvalid = 1'b0;` 与 DUT 抢同一个时钟边沿，导致 DUT 根本没收到数据。
两处都是先得到错误结论、再定位修好的——**这正是"证据要能复查"的意义**：
如果只记录"检出率 100%"，这两个坑会一直藏在测试台里。

证据：`.iverilog-ai/external/uart_rx_check/evidence.json`；复现命令
`python scripts/fetch_external_modules.py` + `python scripts/check_external_module.py`；
口径与来源见 `docs/experiment/external_results.md` 与 `docs/experiment/metric_inventory.md`。

## 六、创新性与开放价值

### 6.1 创新性

与"让大模型直接写 testbench"的常见方案相比，本项目的实质改进有三条：

**（0）与已有方案的对比选型**

| 方案 | 谁在判对错 | 不需要用户写 TB | 判定可复现 | 成本 | 我们相对它的差异 |
|---|:---:|:---:|:---:|---|---|
| 人工手写 testbench | 人 + 仿真器 | ✗ | 是 | 每个设计 80 行起 | 我们**用同一套判据免掉写 TB**，但保留人工边界激励的位置（消融实验显示它仍更强） |
| 通用大模型直接写 TB | **模型自己**（它同时给期望值） | ✓ | 否 | 低 | **判决权从模型手里拿走**：AI 写的期望值被参考模型复算覆盖，不一致只记诊断 |
| 商业仿真器的 AI 助手 | 仿真器 | 部分 | 是 | 授权费 + 闭源 | 我们**全链路可审计**（判决路径、四层结论口径、逐条证据），且离线可跑、零授权成本 |
| 形式化等价验证 | 求解器 | ✓ | 是 | 需形式化建模 | 我们**不做等价证明**，只证明"在测试计划覆盖范围内行为一致"——门槛与成本低一个量级 |

   期望值会被确定性参考模型复算覆盖。这不是提示词技巧，而是架构上的分工。
2. **证据分层与负向声明。** 主动写出未做的证据层级（时序/比特流/上板），并把"综合通过
   ≠ 时序收敛 ≠ 能上板"作为固定免责声明写入报告与网页。
3. **噪声校准与失败公开成为交付物的一部分。** 静态规则与波形分析都公开了误报校准过程；
   在线模型实验公开了 9 个未检出缺陷及逐条原因，而不是只报最佳成绩。

## 八、总结与展望

### 8.1 项目总结

本项目围绕 Icarus Verilog 构建了一套"**AI 提出、开源工具裁决**"的验证工具链：可运行的
命令行与网页；15 案例 / 83 缺陷基准集（实跑 **83/83 检出、0 误报、0 不可判定**）；
15/15 参考模型逐拍对齐；44 条静态规则（逐条正反例 + 噪声校准）；波形语义分析、分层证据、
行为对比三套深度能力；**三组离线消融实测与并集推导**检验了规则激励与参考模型的作用，
真实 LLM 的结果单独披露；当前回归结果见 `docs/experiment/local_validation_2026-10-04.md`。
离线确定性流程可复现；在线计划生成依赖外部模型，须保留计划和响应以便重放执行。

**主要价值**：把"AI 辅助验证"从"相信模型"变成"用开源工具裁决模型提出的假设"，并把这个
过程中的失败、误报与边界如实公开——包括那条对我们不利的结论（规划器没有多检出任何一条
人工边界激励覆盖不到的缺陷）。

**未完成事项**：时序与上板证据层（需器件库与硬件，超出本周期条件）；上游社区贡献；
更广泛的第三方工具适配；对象③④的用户调研。

**团队收获**：理解了 IEEE 1364 非阻塞赋值的实际影响（8 个模型错误中有 3 个源于此）；学会把
"工具报出的数字"与"数字里有多少是真的"分开评估；体会到"如实说明没做什么"比"多报一个
指标"更能提高可信度。

### 8.2 后续计划

① 扩展案例与缺陷类型（优先协议类与跨时钟域类），并把参考模型对齐方法固化为可复用流程；
② 为其他开源仿真器（Verilator、GHDL 等）提供执行层适配，使基准集与测试计划格式可跨工具
复用；③ 完善教程与在线演示，降低他人复用门槛，并在权利边界清晰的前提下向上游社区介绍
本项目与基准集。

### 9.11 静态规则与波形判据的三轮校准（正文 §5.4 的展开）

**静态规则**：初版 9 条规则、对仓库 84 个 RTL 文件报出 317 条命中，逐条核实后修掉：
`division-operator` 把注释结尾 `*/` 当成除法（84/84 全命中）、`inferred-latch` 把合法写法
误判为锁存器（15 条 error 级误报）、`missing-timescale` 因注释剥离而全命中、时钟/复位名
只匹配前缀（`rst*`）导致实际命名 `rst_n` 从不命中。校准后：44 条规则、163 条命中、
**0 条 error 级误报**。

**波形毛刺判据**：初版按翻转次数误报时钟与计数器；第二版用"短于全局中位数 1/3"误报
`busy` 的正常窄脉冲。第三版采用全局基线、连续 ≥3 个异常间隔并排除复位沿，在已测时钟、
计数器、脉冲与双峰样例上无误报，连续快翻仍可命中。
