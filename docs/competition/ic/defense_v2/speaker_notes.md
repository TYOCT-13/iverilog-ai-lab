# ICARUS 答辩讲述稿

建议讲述 5–7 分钟。用自己的语速讲清楚因果，不逐字读页面上的所有指标。结果来源见 `data.json` 和各页备注；第 11 页对应 `c7bb280` 的三次重复原件。当前文件不代表真人试用或独立人工审核已完成。

## 01 数字 IP 验证智能体

ICARUS 针对小型数字 IP 的测试规划与仿真复核。模型通过第三方 API 提出测试输入，受控执行器用 Icarus 运行真实 RTL，再由明确的参考模型或人工规格判据检查结果。项目没有训练自己的基础模型，也不把模型的自然语言结论当作电路正确性的证明。

## 02 数字 IP 的验证需求

能生成可运行的输入，只解决了验证的第一步。复位、FIFO 空满边界、UART 的完整串行帧，以及握手缓存的反压，都有具体的时序条件。我们的需求分析来自这些案例的执行和失败记录，没有虚构行业访谈或节省时间的百分比。面向数字电路学习者、小型 IP 开发者，以及需要复核记录的人。

## 03 API 规划与仿真裁决

四个环节各自负责一件事。人工规格说明什么行为是正确的，API 决定下一组输入，执行器检查权限和预算后调用 Icarus，判据对实际输出作比较。模型只能追加输入或者停止，不能替换 DUT、修改旧向量、改变正确答案或随意执行命令。每轮把真实仿真结果和覆盖缺口反馈给模型，再决定是否补测。

## 04 动作权限与预算

预注册实验给四个模块不同的累计激励周期上限。UART 和 SPI 必须等待较长的事务完成，不能拿同样的短向量数假定它们得到同等测试。每轮追加、总向量、轮数、请求数、超时和累计周期都受限制。网页允许用户自行设置预算，截图中的默认值不是预注册实验的执行配置。

## 05 逐周期采样与功能场景

当前实现记录 24 个有限命名场景，分布为 FIFO 7 个、UART 6 个、SPI 6 个和握手缓存 5 个。记录依据测试台实际采样的输入与输出，同时校验 RTL、计划、合约和测试台的工件身份。我们分别描述输入尝试、输出状态与完整协议序列；没采到、出现未知逻辑值或工件不匹配时保留未知。场景命中只说明测试到过该行为，不能替代功能正确性或 RTL 代码覆盖率。

## 06 FIFO 的真实反例

旧 RTL 与旧参考模型曾共享一个错误，因此它们彼此一致仍然可能都不符合队列规格。独立队列验证在第 5 拍同时读出 25、写入 99，队列从 `[25,66]` 变为 `[66,99]`，占用量仍是 2。旧计数更新少记一次，到了第 7 拍，实际 `full=0`，独立队列应为 1。修复后这一点为 1，同样 76 周期、228 次输出比较从 66 次差异变为 0。两个重新从正确基线制作的单点错误控制仍然触发差异，所以没有把判据改松来获得一致。

## 07 外部变体重放

外部重放固定 24 个候选模块，分别来自 UART RX、UART TX 和优先编码器。每个家族都有正确基线、历史人工错误变体、等价改写和编译失败控制。UART TX 原判据只检查有限事件，漏了位持续时间和 busy 不释放的问题。补全这些人工判据后，同一 15 个人工错误变体的检出从 13 个增加到 15 个。这里的收益来自判据改进，不是 API。三个家族来自同作者的两个仓库，也不是独立留出测试。

## 08 真实操作入口

网页提供案例选择、上传、验证目标、测试规划、仿真和结果查看。右侧是冻结版本 `28be1ed` 的 r3 网页预算与覆盖开关，只做像素裁切。左侧数字来自一次离线 UART 执行：29 个向量，58 次比较全部一致，切换页面后结果保留。三种浏览器视口没有横向溢出，手机是桌面浏览器模拟，并未声称测试了真实手机或真人使用。此前脚本定位与旧服务缓存的问题记录仍保留，最终 r3 在重启服务后完成；切页保留不等于重启进程保留内存会话。全仓回归为 1073 项通过、2 项跳过、0 失败，mypy 检查 76 源文件无误。这些是工程检查，在线 API 的能力由实验原件单独说明。

## 09 运行证据与离线重放

每次运行都保存 RTL、计划、测试台、日志、波形和采样记录，也保存 API 轨迹及停止原因。哈希能检查复核是否用了相同工件，逐周期记录能定位首个差异。旧证据包曾在同一主机从冻结 ZIP 解包重放，0 次 API 请求、547 次输出比较、0 次差异。这是一次机器复核，新 v2 证据另存；它不能被称为独立人工审核。

## 10 历史 pilot

这页保留源码 `e9b7b8a` 的历史结果。在 4 个模块、8 个开发集缺陷、一次重复下，固定模板和随机各检出 5 个，单次 API 检出 2 个，反馈 Agent 检出 4 个，无反馈 Agent 检出 2 个。60 行记录包含 52 次真实 API 请求。这个结果证明流程可以真实执行，但没有证明 Agent 普遍提高了检出率。后来 RTL、判据、协议规格、周期预算与采样都变过，不能把新旧差异解释成单独一种改进的收益。

## 11 Agent v2 的实际执行范围

源码 `c7bb280` 的本轮记录保留 252 个任务、七策略和三次重复的完整分母，每策略每次 8 个缺陷。本地固定模板每次检出 7 个，均匀和协议随机每次检出 8 个。API 组明显较低，主要受到动作输出被严格格式校验拒绝的影响；137 行为 `policy_error`，125 行完全没有仿真轮。本轮确实发生 157 次 API 请求，但不能表述成全部任务都执行了仿真，也没满足各任务都有仿真原件的内部比较条件。失败均保留，不能宣布 AI 或覆盖反馈已带来增益。此前 `598e6dc` 的高强度思考/截断预跑，以及之后的新版本联调都另存，不替换这一批结果。

## 12 v4 的一次联调与局限

最后一页是不同源码 `28be1ed` 与 v4 提示格式的一次开发烟测，单列 84 个任务，不替换上一页 c7 的三次结果。实际发生 94 次请求，上限 120，共 201710 tokens；94 个动作全部通过严格 schema，0 拒绝。固定模板检出 7/8，均匀随机和协议随机各 8/8，单次 API 2/8，反馈 Agent 6/8，无反馈 Agent 7/8，无覆盖反馈 Agent 5/8。仍有一个正确 UART 基线在单次 API 策略下发生测试台生成错误，没有仿真轮，因此不能说所有正确基线已通过，内部完整证据条件仍未满足。动作结构接通不等于测试执行或功能判定全部成功。

反馈 6/8 和无覆盖反馈 5/8 来自独立随机提案，一次重复且实际请求与周期不同，不能证明覆盖反馈的因果收益；无反馈 7/8 也不支持“反馈一定提高检出”的结论。Agent 仍未超过本地随机基线。当前结论只适用于有限开发集、已执行输入和已审计参数，下一步是独立留出模块、多次重复、H01 真人任务计时与原始反馈，以及 H02 独立人员复核和跨主机重放。机器证据帮助复现这些工作，不能补成真人或人工结论。

## 常见追问

**AI 主要贡献是什么？** 自动根据接口、规格和真实反馈提出补测输入，并在预算内组织验证循环。正确性判据、执行权限和实验分母仍由工具与审计规则控制。

**为什么检出比随机低也保留？** 已执行的失败和未检出是评估证据。小型开发集不能支持普遍优势的结论，保留结果比筛除结果更便于判断后续改进是否有效。

**覆盖是不是 100%？** 24 个场景是有限功能场景集合；命中率不是电路所有状态、RTL 代码覆盖或正确性保证。未知样本也不能当成未触发的零值。

**外部 15/15 能说明通用验证吗？** 不能。它来自有限、人工构造的历史变体和有限参数形状，且新增收益来自人工 UART TX 判据。

**是否已完成真人和人审？** 目前没有提供真实原件，不作通过声明。自动浏览器检查、AppTest 与同主机重放分别按各自证据类型展示。
